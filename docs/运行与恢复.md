# 运行与恢复

## 本机启动

使用 PowerShell 7，在本项目目录执行 `./scripts/start.ps1 -Build -PrepareDemo`。首次初始化只写入独立 `jingyue_ticket_dev` 数据库与本项目 `.runtime`。后续不需要 `-PrepareDemo`；该选项只预热原演示票种的草稿，不覆盖已有库存，不恢复运营主动暂停的批次。

入口为 **http://127.0.0.1:5190**。接口为 `http://127.0.0.1:8089/api/v1`，前端代理保留完整路径。不要直接双击 index.html，也不要打开旧 hmdp 或 travel-ticket-web 页面。

本地依赖：JDK 17（Java 8 字节码）、Maven 3、MySQL 8、Redis 7（支持 Stream）、Node 20、PowerShell 7。Windows 工具路径在 scripts 中可配置。开发 Kafka 通过 Maven 测试依赖启动一个独立 broker 与内嵌 ZooKeeper；不是生产高可用部署。

| 服务 | 地址 / 数据 |
| --- | --- |
| 新前端 | 127.0.0.1:5190 |
| 新后端 | 127.0.0.1:8089 |
| 新 MySQL | 127.0.0.1:3318 / jingyue_ticket_dev |
| 新 Redis | 127.0.0.1:6398 / db0 / jy:v1 命名空间 |
| 新 Kafka | 127.0.0.1:19092 / jingyue-ticket-orders-v1 / jingyue-ticket-v1 |

`.runtime/env.ps1` 由初始化脚本生成数据库口令和持久票券签名密钥，启动前 dot-source。这些文件不提交。不要重建或轮换签名密钥后期待历史二维码仍可核销；演示历史数据与原签名密钥需要一起保存。

### 演示账号

登录框选择账号 → 获取验证码 → 登录。不发送真实短信，验证码一次使用、120秒有效。验证码只在开发模式的以下账号下返回。

| 手机号 | 角色 | 范围 |
| --- | --- | --- |
| 13900000001 | 普通用户 | 仅本人申请、订单与票券 |
| 13900000002 | 运营 | 景点、票种、批次、对账、异常和审计 |
| 13900000003 | 核销员 | 岚溪青岚谷 |
| 13900000004 | 核销员 | 栖川云水古镇 |

主流程：景点 → 票种与日期 → 阅读并勾选须知 → 预约抢购 → 当前页自动出现“下单完成，待支付” → 模拟支付 → 电子票 → 对应核销员粘贴凭证核销。已支付、已核销、已过期订单保留限购资格；仅未支付关闭且归还完成后可重购。

运营新批次：创建景点 → 创建票种 → 配置日期SKU → 预热 → 发布。草稿、已预热都不能下单；发布后价格、日期、总库存冻结。暂停操作显示处理中，后台可靠关闭 Redis 后才完成。恢复只打开销售，不重置剩余库存。

### 标准环境手动部署

脚本默认路径针对当前 Windows 开发机。其他机器可直接使用标准命令：

1. 启动独立 MySQL 8、Redis 7 与 Kafka，创建新库和专属低权限账号，按文件名顺序执行 `backend/src/main/resources/db/*.sql`。
2. 配置 `JINGYUE_MYSQL_HOST/PORT/USER/PASSWORD`、`JINGYUE_DATABASE`、`JINGYUE_REDIS_HOST/PORT/PASSWORD`、`JINGYUE_KAFKA`、`JINGYUE_TICKET_SIGNING_KEY`（至少32字符）。开发演示另设 `JINGYUE_DEVELOPMENT=true`、`JINGYUE_MOCK_PAYMENT=true`。非演示环境默认关闭。
3. 新建16分区主题 `jingyue-ticket-orders-v1`。单broker仅适合演示。实际多broker需配置副本数、min.insync.replicas和访问控制，并另行故障验收。
4. 在 backend 执行 `mvn package -DskipTests`；运行生成的 Spring Boot jar。先确认 `/api/v1/health`，再显式预热发布日期批次。
5. `node frontend/server.mjs` 启动同源前端。端口由 `JINGYUE_PORT` 和 `JINGYUE_WEB_PORT` 配置。

## 测试

加载 `.runtime/env.ps1` 后，在 backend 执行 `mvn test -Dtest=TicketIntegrationTest`，需要真实 MySQL、Redis、Kafka。本地测试会使用带“独立验收数据”描述的产品；测试结束停止其销售并隐藏验收景点，不删除历史订单、请求结果或幂等证据。

`node scripts/performance.mjs 3500` 为真实鉴权 HTTP 突发测试，预建连接，单独统计有效受理、HTTP结果、写出请求后等待响应峰值和最终落库。不将连接数、429或售罄计为有效吞吐。会生成独立性能数据及 output/verification JSON，结束暂停并隐藏该景点。

`node scripts/verify-kafka-outage.mjs` **会终止本项目开发 Kafka 60秒后恢复**，验证待发送、过期采样背压和同订单重投。仅允许在隔离演示环境执行；脚本核对记录进程与运行目录，不停止旧业务 Kafka。

## 故障排查

| 现象 | 检查与恢复 |
| --- | --- |
| 网页打不开 | 确认5190监听，运行新 frontend/server.mjs；检查 `.runtime/frontend*.log`，不能用 file:// |
| 受理429 | 看运营对账的 Redis outbox、Kafka lag、采样时间与配额；不要关闭鉴权或绕过库存 |
| 排队超过60秒 | 查看原请求与异常记录；60秒关注、5分钟告警，不按超时直接退款或重新下单 |
| Kafka不可用 | 保留 Redis journal/Stream；恢复专属broker后原订单号重投；不要 XDEL 待确认事件 |
| 批次SQL失败 | 整批回滚；逐条重试或可靠保存原消息与位置后隔离；查异常记录，运营重试会写审计 |
| 订单关闭但不可重购 | 看 RELEASE 数据库待办；Redis确认原订单归还后 releaseState 才为 RELEASED |
| Lua执行中断 | 保留 fence、repair 与 releaseRepair；恢复任务按同订单证据继续。不能假设 Lua错误会撤销之前的命令 |
| Redis元数据/库存丢失 | 停止该SKU；曾预热批次不能从落后MySQL再预热。冻结、核对原请求/订单/资格/事件后制定恢复方案 |
| 缓存未更新 | 看 CACHE 数据库待办与版本；提交后重试失效，广播清L1，漏广播由30秒本地TTL兜底 |
| 核销失败 | 先查角色与景点scope，再查PAID、有效窗口与首次核销流水；过期扫描延迟也不允许越期使用 |

## 回滚与数据保护

先暂停新受理，排空或冻结已受理事件与归还任务，完成对账，再停止后端。`stop-backend.ps1` 校验记录PID与本项目jar路径，保留持久数据。`stop-local-kafka.ps1` 请求正常关闭；`-Crash` 仅用于故障测试。

旧优惠券服务不能接管新票务事件。不要删除新库、Redis AOF、Kafka日志、请求结果、归还去重记录或签名密钥来“回滚”。完整Redis丢失、AOF everysec最后一秒丢失与单broker故障不是零丢单高可用方案，本版本不作该承诺。


## 新增验收与交付入口

`node scripts/load-acceptance.mjs 3000 60`：固定目标受理负载，记录驱动未发出、有效受理、429、延迟和最终审计。发生器的队列上限也算未达目标。

`node scripts/load-likes.mjs 3000 60`：每个用户顺序发送明确目标，热点/分散游记交替，只有确认的状态变化计吞吐。

`node scripts/load-mixed.mjs 1800 50`：1000鉴权虚拟用户、50个购票意图/秒，真实15分钟支付窗口；85%模拟支付、10%取消、5%自然超时；今日票部分核销。每10秒采样资源，最终检查库存、资格、票款和核销。

`python scripts/package-source.py`：仅打包允许的源码、文档和原始验收数据，不包含.runtime、.env、上传文件、构建产物或依赖目录。

Docker的独立配置见根目录compose.yaml。`node scripts/init-compose-env.mjs`只生成一次本机.env；不要与原生实例同时占用相同端口，不要以删除数据卷作为常规回滚。
