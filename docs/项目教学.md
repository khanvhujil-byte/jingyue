# 景约项目教学

先跑通“选景点 → 选日期 → 提交申请 → 模拟支付 → 查看电子票 → 授权核销”，再读实现。各章按问题、源码和练习展开，组织方式参考 [Hello Agents](https://github.com/datawhalechina/hello-agents) 从概念到实现的学习顺序。

## 第一章：先认清一次请求

页面来自 Vue，入口是 [frontend/index.html](../frontend/index.html)，交互在 [frontend/app.js](../frontend/app.js)。路由使用 `#/`、`#/attractions/{id}` 等 hash，不要求服务端渲染。

浏览器的 `api()` 统一发送 `/api/v1` 请求。[Node 代理](../frontend/server.mjs)把完整路径转发给 Spring Boot；[CatalogController](../backend/src/main/java/com/jingyue/CatalogController.java)处理景点与日期日历。前端直接运行，不需要打包。

**练习**：在开发者工具中从点击景点开始，分别找到详情、日期日历和相关游记请求，解释它们为什么可以并行读取。

## 第二章：为什么门票要拆成日期 SKU

一个景点可以有多个票种，一个票种对应多个日期库存。景点介绍、票种说明和可卖的某一天不是同一个实体。

先读 [001-ticket.sql](../backend/src/main/resources/db/001-ticket.sql) 中的 `tb_ticket_product`、`tb_ticket_sku`、`tb_ticket_order`。SKU 保存日期、售卖时间、使用窗口、价格、总库存和批次标识；订单保存购买时的快照。

运营入口在 [AdminController](../backend/src/main/java/com/jingyue/AdminController.java)。新批次先创建，再预热、发布；暂停与恢复销售沿用既有库存。已发布批次的价格、日期和总库存冻结。

**练习**：说明为什么 10 月 20 日和 21 日要分开扣库存，以及修改景点介绍为何不应改写已生成订单的金额。

## 第三章：身份与权限在哪里生效

[AuthController](../backend/src/main/java/com/jingyue/AuthController.java)提供验证码、登录和注销。演示验证码只在开发模式的指定账号下返回；登录后生成随机 token，身份保存在 Redis。

[AuthFilter](../backend/src/main/java/com/jingyue/AuthFilter.java)读取 Bearer token，将身份放入 [Identity](../backend/src/main/java/com/jingyue/Identity.java) 的线程上下文，并在请求结束清理。购买用户、运营管理员、核销员的权限由后端校验；核销员还受景点授权范围限制。

**练习**：请求体伪造 `userId` 或 `role` 为什么不能改变身份？只在前端隐藏“运营台”为什么不够？

## 第四章：受理成功承诺了什么

[TicketAdmission.submit()](../backend/src/main/java/com/jingyue/TicketAdmission.java)先处理请求身份和原结果，再执行 [accept.lua](../backend/src/main/resources/lua/accept.lua)。脚本检查销售状态、时间、库存、资格和限流。

预扣记录、购买资格、请求结果、原事件和恢复信息在同一业务 Hash 中提交，Stream 充当投递索引。不要假定 Lua 报错会自动撤销已经执行的写命令；[repair.lua](../backend/src/main/resources/lua/repair.lua)与恢复任务依据原证据继续处理。

此时返回 `PROCESSING`，还没有支付，也没有有效票券。相同用户使用原 `clientRequestId` 重试，必须得到同一操作的结果；更换 SKU 却复用该请求号会发生冲突。

**练习**：把 Redis 成功后、HTTP 返回前的网络断开画出来，解释前端应保留什么，为什么不能直接创建新请求号。

## 第五章：如何把已受理事件交给 Kafka

读 [TicketPipeline](../backend/src/main/java/com/jingyue/TicketPipeline.java) 的投递、恢复和消费流程。发送服务保留原订单身份，收到 broker ACK 后才清理待投递信息；发送超时仍可能已经到达 broker，所以恢复时允许重复发送。

消费者收到消息后交给事务下单；数据库提交后才确认消费位置。无法处理的消息要持久保存原内容和位置，再进入受限异常处理流程。Kafka ACK、消费确认和数据库提交分别回答不同的问题。

**练习**：列出“broker 已收到但发送端未收到 ACK”和“数据库已提交但 offset 未确认”的恢复动作。

## 第六章：重复消费如何不重复扣库存

[TicketWriter](../backend/src/main/java/com/jingyue/TicketWriter.java)对消息做身份、版本和业务校验，按稳定顺序获取 SKU 锁，再在事务中建立请求结果记录、扣库存、写订单及有效购买资格。

数据库请求结果按订单身份唯一。已创建与已持久拒绝的身份都不能由迟到消息重新创建；历史已关闭订单也不能因为旧创建消息重放再次扣库存。

**练习**：分别说明数据库唯一约束和业务请求结果记录的作用。为什么只给订单 ID 加唯一索引，还不足以表达持久拒绝？

## 第七章：取消订单为什么不是简单加一

在 [OrderService](../backend/src/main/java/com/jingyue/OrderService.java)中追踪关闭未支付订单的事务：改状态、归还数据库库存、删除原订单资格、写归还待办。

[release.lua](../backend/src/main/resources/lua/release.lua)在 Redis 核对 SKU 批次和原订单，使用永久去重证据归还一次。只有 Redis 确认后才把归还标记为完成；重购资格由这条完整链路决定。

**练习**：用户取消 A、库存归还后购买 B，此时 A 的归还事件重放，怎样保证 B 的资格仍保留？

## 第八章：支付、电子票与核销

继续读 [OrderService](../backend/src/main/java/com/jingyue/OrderService.java) 的模拟支付、票券查询和核销。支付和取消竞争同一订单，按照一致顺序加锁，只有一种结果可以提交。

金额来自订单快照。成功支付记录与电子票分别按订单唯一；票券凭证包含随机信息和 HMAC-SHA256 签名。核销必须同时通过角色、景点范围、未使用状态及有效窗口检查，唯一流水防止重复核销。

**练习**：解释重复支付、支付与取消并发、重复核销、跨景点核销，各自由哪一层约束保护。模拟支付演示了状态机，不代表接入了真实支付平台。

## 第九章：公共缓存与游记互动

[CatalogCache](../backend/src/main/java/com/jingyue/CatalogCache.java)组织 Caffeine 和 Redis 景点缓存。运营更新通过数据库待办触发版本与缓存失效重试，广播清理各实例本地缓存，TTL 处理漏广播。交易库存和登录状态不使用这层公共详情缓存。

[NotesController](../backend/src/main/java/com/jingyue/NotesController.java)处理游记、上传和明确的点赞目标。点赞复用 [AsyncBlogLikeService](../backend/src/main/java/com/hmdp/service/like/async/AsyncBlogLikeService.java)、[LikeBatchProjector](../backend/src/main/java/com/hmdp/service/like/async/LikeBatchProjector.java) 和 [LikeShardRouter](../backend/src/main/java/com/hmdp/service/like/async/LikeShardRouter.java)，用版本处理重放，将关系状态投影到 16 张表。

**练习**：解释为什么“设置 liked=true”比“收到一次请求就翻转一次”更适合重试；缓存失效失败时为什么要保留数据库待办。

## 第十章：前端恢复与独立验证

回到 [frontend/app.js](../frontend/app.js)。前端在 sessionStorage 按用户与 SKU 保存原申请，刷新、切换日期和网络恢复时先查询。`UNKNOWN` 表示结果未确认，不是可以安全重发的失败。订单创建后页面才显示待支付，支付后才读取电子票。

[TicketIntegrationTest](../backend/src/test/java/com/jingyue/TicketIntegrationTest.java)覆盖订单生命周期、重复请求、库存争抢、支付取消竞争、故障恢复和最终一致性。它会创建真实测试数据，必须使用独立数据服务。

[GitHub Actions](../.github/workflows/ci.yml)创建专属 MySQL、Redis、Kafka，执行集成测试和打包。前端是直接运行的 Vue 文件，使用 `node --check` 检查脚本，再在浏览器验证实际交互。部署见[部署说明](部署说明.md)。

**练习**：在独立环境记录一次购票的 `clientRequestId`、订单 ID、SKU、Redis 记录和数据库结果，沿链路解释每一步的状态变化。最后区分源码编译通过、功能测试通过和达到目标吞吐这三种证据。
