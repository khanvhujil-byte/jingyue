# 景约项目教学

从一次页面请求开始，逐步理解登录、缓存、秒杀资格、事件投递、数据库事务和前端状态。每章先说明要解决的问题，再给出源码入口和练习。阅读顺序参考 [Hello Agents](https://github.com/datawhalechina/hello-agents)由概念到实现再到实践的组织方式，示例对应本项目。

先按 [README](../README.md#本地运行)启动页面。有完整运行环境后，再切到真实服务观察请求。

## 第一章：从页面到数据库

**目标：** 建立分层架构和数据流的认识。

在页面浏览一个目的地，再打开它的详情和活动票种。在真实模式下，从浏览器 Network 中找出分类、详情、票种列表请求。

```text
浏览器 → /api → 开发代理或 Nginx → Controller
       → Service → Mapper → MySQL
                 → Redis / Caffeine
```

阅读入口：

- [HmDianPingApplication.java](../src/main/java/com/hmdp/HmDianPingApplication.java)：应用、Mapper、调度与 Kafka 的启用。
- [ShopController.java](../src/main/java/com/hmdp/controller/ShopController.java)：目的地兼容接口。
- [ShopServiceImpl.java](../src/main/java/com/hmdp/service/impl/ShopServiceImpl.java)：查询与缓存逻辑。
- [ShopMapper.java](../src/main/java/com/hmdp/mapper/ShopMapper.java)：数据访问。
- [api.js](../frontend/src/api.js)：前端真实接口适配。

文旅页面沿用后端的 `shop`、`voucher` 和 `blog` 命名。阅读时分别对应目的地、活动票种和旅行手记；当前实现保留了原有数据契约。

**练习：** 跟踪 `GET /shop/{id}`，写出请求参数、调用的 Service、访问的数据，以及返回的 `Result` 字段。再比较体验模式与真实模式的入口。

## 第二章：登录态如何跨请求保存

**目标：** 理解用户身份如何从一次登录传递到之后的业务请求。

[UserServiceImpl.java](../src/main/java/com/hmdp/service/impl/UserServiceImpl.java)负责验证码校验、创建用户、生成 token，以及将用户摘要写入 Redis Hash。token 对应的登录数据有过期时间。

后续请求在 `authorization` 中携带 token。两个拦截器按先后顺序执行：

1. [RefreshTokenInterceptor.java](../src/main/java/com/hmdp/utils/RefreshTokenInterceptor.java)读取登录数据、续期并恢复当前用户。
2. [LoginInterceptor.java](../src/main/java/com/hmdp/utils/LoginInterceptor.java)检查当前接口是否需要登录。

当前请求的用户放在 [UserHolder.java](../src/main/java/com/hmdp/utils/UserHolder.java)的 ThreadLocal 中。请求结束时清理，防止线程池复用线程后留下上一次请求的身份。顺序由 [MvcConfig.java](../src/main/java/com/hmdp/config/MvcConfig.java)配置；登录读取与续期的脚本是 [login_refresh.lua](../src/main/resources/login_refresh.lua)。

ThreadLocal 的作用域是当前执行线程；它不能自动把用户身份传入 Kafka 消费线程。订单事件因此明确携带 `userId`。

**练习：** 对比匿名查看目的地、匿名发起抢购、登录发起抢购三种请求，沿拦截器判断它们分别在哪里放行或拒绝。解释为什么每次请求结束都要清理用户。

## 第三章：查询与缓存

**目标：** 理解缓存保存的内容、失效条件以及回源顺序。

店铺查询和票种查询各有缓存实现：

| 入口 | 主要内容 |
| --- | --- |
| [CacheClient.java](../src/main/java/com/hmdp/utils/CacheClient.java) | 空值缓存、互斥重建、逻辑过期工具 |
| [ShopServiceImpl.java](../src/main/java/com/hmdp/service/impl/ShopServiceImpl.java) | 目的地缓存读取与更新 |
| [VoucherListCacheService.java](../src/main/java/com/hmdp/service/cache/VoucherListCacheService.java) | MySQL、Redis、Caffeine 三种票种列表查询模式 |
| [VoucherCacheProperties.java](../src/main/java/com/hmdp/config/VoucherCacheProperties.java) | 刷新、过期和 Redis TTL 配置 |

先分清几个概念：空值缓存表示查询过但没有记录；互斥重建控制热点失效时的回源；逻辑过期将业务过期时间放入缓存内容；Caffeine 的刷新与硬过期则分别决定何时加载新值、何时不能继续返回旧值。

票种列表属于展示数据。真正抢购还要进入独立的资格与库存检查，不能仅凭列表中展示的库存做扣减。

**练习：** 沿 `getVoucherByShopId()` 比较三种模式的读取路径。记录 `refresh-after-write`、`expire-after-write` 和 `redis-ttl` 影响的是哪一层数据。

## 第四章：受理一次抢购

**目标：** 理解库存预扣、一人一单和事件保存之间的关系。

从 [VoucherOrderController.java](../src/main/java/com/hmdp/controller/VoucherOrderController.java)进入 [VoucherOrderServiceImpl.java](../src/main/java/com/hmdp/service/impl/VoucherOrderServiceImpl.java)。服务读取已认证用户、生成订单号、检查库存是否已预热，然后执行 [seckill.lua](../src/main/resources/seckill.lua)。

脚本检查键类型、库存格式、限流、剩余库存、用户购买资格和待办容量。成功受理时，修改库存与购买资格，并写入 Redis Stream 待办。

```text
库存和资格检查 → 保存恢复记录 → 预扣库存、记录购买资格
               → 标记 READY → 保存待发送事件 → 清理恢复记录
```

Lua 执行期间不会被其他命令交错，但运行时错误不会自动撤销此前写入。因此实现先检查数据类型，再使用恢复记录保护多步写入。

恢复状态有不同含义：

| 状态 | 恢复方向 |
| --- | --- |
| `PREPARED` | 还未完成受理，可恢复原库存与资格 |
| `READY` | 资格写入已经完成，继续保证事件可投递 |

[SeckillReservationRecovery.java](../src/main/java/com/hmdp/service/order/SeckillReservationRecovery.java)和 [seckill-recover.lua](../src/main/resources/seckill-recover.lua)处理待恢复记录。库存通过 [SeckillInventoryWarmup.java](../src/main/java/com/hmdp/service/order/SeckillInventoryWarmup.java)安全预热；创建票种后由事务提交回调触发。

HTTP 返回订单号表示请求已经受理。数据库中是否已有订单，要通过之后的状态查询确认。

**练习：** 阅读 [SeckillReservationRecoveryTest.java](../src/test/java/com/hmdp/order/SeckillReservationRecoveryTest.java)，找到“预扣后失败”和“事件已写入后失败”的案例，解释为什么它们不能都做库存加一。

## 第五章：把事件送到 Kafka

**目标：** 理解发送失败、确认超时和重复投递的处理方式。

[SeckillOutboxPublisher.java](../src/main/java/com/hmdp/service/order/SeckillOutboxPublisher.java)定期读取 Redis Stream 中的待发送事件，组装订单消息并发送到 Kafka。

它先提交一批发送任务，再等待发送结果，只删除获得确认的事件。失败或结果不明的事件继续保留。

考虑一个时序：Kafka 已收到消息，进程在删除 Redis 待办前退出。下一轮还会发送同一条事件，因此后续消费者必须支持重放。发送确认和数据库幂等需要共同工作。

[KafkaConfig.java](../src/main/java/com/hmdp/config/KafkaConfig.java)配置发送确认、生产者幂等、手动消费确认，以及失败后重新处理。

**练习：** 在 [SeckillReliabilityIntegrationTest.java](../src/test/java/com/hmdp/order/SeckillReliabilityIntegrationTest.java)中找到 broker 失败、发送结果不明和重复消费案例。为上面的退出时序画出事件可能出现的位置。

## 第六章：事务下单与订单状态

**目标：** 理解数据库边界和消费确认顺序。

[SeckillVoucherConsumer.java](../src/main/java/com/hmdp/consumer/SeckillVoucherConsumer.java)解析订单事件，调用独立业务服务，业务调用成功返回后才确认消费。

[VoucherOrderWriter.java](../src/main/java/com/hmdp/service/order/VoucherOrderWriter.java)在一个数据库事务中完成：

1. 校验事件身份字段。
2. 锁定对应票种库存行。
3. 检查相同订单号是否已落库，以及其业务身份是否一致。
4. 检查用户是否已有该票种订单。
5. 通过条件更新扣库存，再插入订单。

检查、库存扣减与订单创建属于同一事务。事务完成后消费者才确认，异常会传播给消费运行时。数据库还保留订单主键和 `(user_id, voucher_id)` 唯一约束。

[VoucherOrderBatchWriter.java](../src/main/java/com/hmdp/service/order/VoucherOrderBatchWriter.java)与 [SeckillVoucherBatchConsumer.java](../src/main/java/com/hmdp/consumer/SeckillVoucherBatchConsumer.java)提供可选批处理路径。

页面查询由 [VoucherOrderStatusService.java](../src/main/java/com/hmdp/service/order/VoucherOrderStatusService.java)提供：有已提交订单返回 `CREATED`，已有资格但尚无订单返回 `PENDING`，没有足够依据时返回 `UNKNOWN`。

**练习：** 假设数据库提交成功、Kafka offset 确认前进程退出，下一次消费如何处理？再阅读 [VoucherOrderWriterTest.java](../src/test/java/com/hmdp/order/VoucherOrderWriterTest.java)，找出验证库存和订单一起回滚的断言。

## 第七章：并发点赞

**目标：** 区分目标状态、切换操作，以及同步与异步持久化。

前端可以明确提交“点赞”或“取消”。例如重复提交两次 `liked=true`，目标仍是已点赞。相比“把当前状态取反”，明确目标更适合处理重复请求。

默认实现位于 [BlogLikeService.java](../src/main/java/com/hmdp/service/like/BlogLikeService.java)：先锁定笔记，再读关系、更新关系与计数；事务保证这些写入一起提交。已知锁冲突的重试包住整个事务。

启用异步点赞后，流程变为：

```text
明确目标状态 → Redis Lua 接收状态变化与事件
             → 按笔记 ID 路由 → MySQL 批量投影
             → 提交成功后确认 Redis 事件
```

阅读入口：

- [AsyncBlogLikeService.java](../src/main/java/com/hmdp/service/like/async/AsyncBlogLikeService.java)：接收变更、读取当前状态。
- [like_change.lua](../src/main/resources/like_change.lua)：关系、计数、版本与事件的写入。
- [LikeShardRouter.java](../src/main/java/com/hmdp/service/like/async/LikeShardRouter.java)：按 `blogId % 16` 选择固定状态表与 Redis 前缀。
- [LikeBatchProjector.java](../src/main/java/com/hmdp/service/like/async/LikeBatchProjector.java)：批量处理、事务提交、确认与重放。

取消点赞的版本状态也需要保留，否则晚到的旧点赞事件可能把它恢复。这里是同一 MySQL 数据源中的状态分表。

**练习：** 依次构造“点赞版本 1、取消版本 2、再次收到版本 1”，写出每一步期望状态。验证入口是 [LikeBatchProjectorTest.java](../src/test/java/com/hmdp/like/LikeBatchProjectorTest.java)。

## 第八章：控制请求速率

**目标：** 理解滑动窗口的计数单位与并发边界。

[RateLimiterAspect.java](../src/main/java/com/hmdp/limiter/aop/RateLimiterAspect.java)读取接口上的限流注解，建立限流键并调用 [limiter.lua](../src/main/resources/limiter.lua)。

脚本使用 Redis 的 `TIME` 计算当前窗口：移除过期记录、计算窗口数量、判断上限，再登记本次请求。这些步骤在一次脚本执行中完成。

ZSet 的 score 可以相同，但 member 相同会覆盖旧值。当前实现使用 `INCR` 生成序号，将时间和序号组成 member，因此同毫秒请求也能分别计数。

全局限流、用户限流和待办容量处理不同问题：前两者控制进入速度，容量检查控制积压。它们都不能代替数据库事务和幂等处理。

**练习：** 在同一毫秒登记多次请求，解释为什么随机种子只使用当前毫秒可能产生重复 member。再沿 [RateLimiterBehaviorTest.java](../src/test/java/com/hmdp/order/RateLimiterBehaviorTest.java)检查限流结果与 HTTP 429 的对应。

## 第九章：让页面表达真实执行状态

**目标：** 让前端准确反映请求已受理、仍在处理、已经创建和结果未知。

从 [orders.js](../frontend/src/orders.js)的订单追踪器和 [api.js](../frontend/src/api.js)的错误分类读起。

购买操作先保存追踪记录，再发送 POST。明确拒绝与连接中断分别处理；结果不确定时保留操作记录，后续通过 GET 查询。刷新页面后继续查状态，而不是自动重复发起购买。

订单号使用 Java Long，可能超出 JavaScript 安全整数范围。API 层在解析响应时保留这类 ID，后续以字符串展示和传递。

页面使用有上限的查询与退避，并在隐藏时暂停轮询。体验模式和真实模式各有独立存储，真实服务错误也会如实展示。UI 的入口、路由和事件处理在 [app.js](../frontend/src/app.js)。

**练习：** 对比 HTTP 429、连接超时和 `PENDING` 三种结果。说明哪些可以确定失败、哪些只能继续查询。再运行前端测试，定位大整数解析与防止重复 POST 的断言。

## 综合实践

以一个虚构场馆的限量活动票为例，完成以下练习：

1. 从页面找到票种、购买请求和状态查询。
2. 跟踪用户身份如何进入订单事件。
3. 画出 Redis、Kafka 和 MySQL 中事件与订单的变化。
4. 分别模拟重复购买、重复消息和数据库事务失败。
5. 检查用户看到的状态与已提交数据是否一致。
6. 新增一条回归测试，再构建应用与页面。

完成后，尝试只看一次请求和对应代码，解释它在每个阶段保证了什么，以及下一阶段还需要验证什么。
