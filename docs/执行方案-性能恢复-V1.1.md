# 景约性能恢复：具体执行方案

日期：2026-10-20。状态：PF01、PF03、PF04 已执行，P2 单变量实验进行中。对应[性能PRD](PRD-性能恢复与容量提升-V1.1.md)。单人开发加本机验收预计4–6个工作日；时间是工程估算，不是达到500ms的保证。

## 1. 实施顺序与决策点

| 顺序 | 工作 | 预计时间 | 完成后必须看到的结果 |
|---|---|---|---|
| 0 | 固定口径、补测量、修负载调度 | 0.5天 | 3轮基线可复现，监控不阻塞注入，阶段指标可读取 |
| 1 | 静态Lua脚本与实例复用 | 0.5天 | 业务不变、28项回归通过、脚本资源检查等待显著降低、得到真实HTTP收益 |
| 2 | 有索引的归档队列 | 1天 | 20万历史空待办不再全扫描；迟到终态和失败重试安全 |
| 3 | MQ确认清理和发送窗口 | 0.5–1天 | sender无同步Redis调用，确认/清理积压有界，故障不丢单 |
| 4 | 按测量调批次、路由、线程及查询 | 0.5–1天 | 热点及分散场景均有数据，找出实际稳定容量 |
| 5 | 故障、持续、混合和长时验收 | 1–2天 | G1/G3/G4/G5/G6逐项报告；G2严格500ms单列结论 |

第1步完成后立即汇报三轮结果。如果已经恢复800ms并接近500ms，继续处理历史扫描和持续容量，不急于改请求协议。只有阶段计时证明查库或单Redis成为主要限制，才另开PF09/PF10设计；预计额外2–4天起，不塞入低风险修复。

## 2. 第0步：冻结与补齐测量

**修改位置**：`scripts/performance.mjs`、`scripts/load-acceptance.mjs`、`scripts/load-common.mjs`、`scripts/load-likes.mjs`、`scripts/load-mixed.mjs`、`backend/src/main/java/com/jingyue/ApiMetrics.java`；新增性能配置及记录模板。

1. 保存当前jar和源码SHA、实际启动参数、历史行数、Redis内存、未完成事件数；已有诊断SHA见 `output/verification/performance-diagnosis-20261020/code-baseline-sha256.json`。
2. 保持生产业务实现不变，用同一套脚本跑3轮3500突发。库存至少3500、用户各一次；每轮独立SKU，测前连接池确有3500可复用连接。业务预热使用独立SKU并排空，不消耗正式测试库存；预热时长固定并记录。
3. 在持续负载脚本中移出循环内的 `await api('/admin/metrics')`；监控独立定时，最多一个未完成采样，超时记录缺测。同样修正 `load-mixed.mjs` 与 `load-likes.mjs` 中同步等待监控的调度。将混合旅程的首次立即查询及250/500/1000/2000/4000/5000ms+jitter退避与当前前端对齐，旧脚本首轮等待1秒的结果保留为旧口径。不得为追赶落后的调度在一次循环补发数秒流量。记录每请求计划时刻与实际写出时刻，单独统计未按时注入。
4. 将受理POST和查询GET的计数/延迟分开；用有界聚合直方图记录鉴权、请求查库、Lua往返、broker ACK、清理等待、消费事务与提交。连接获取等待须单独观测，不能把MySQL语句时间当完整查库时间。
5. 诊断采样与正式成绩分开；三轮正式成绩关闭JFR。再用相同采样配置各做一次修复前/后短JFR，比较锁争用路径。

点赞专项另需保存每个 `(userId,blogId)` 的最终期望状态和最后确认版本，并与Redis用户状态及分表逐条核对；若现有接口不返回版本，为测试提供只读审计接口或读取独立验收数据，不能用全局MAX(version)代替逐用户验证。继续核对点赞关系和总计数。

**完成门槛**：结果同时包含计划/实际发送、有效受理、429、业务拒绝、系统错误、客户端在途与服务线程、最终订单和对账；任何未发出的请求都不可忽略。把负载发生器卡顿当成服务拒绝同样错误。

## 3. 第1步：恢复静态Lua加载（第一提交）

**修改位置**：`RedisOps.java`、`TicketPipeline.java`；复用 `com/hmdp/utils/RedisScriptContent.java`。

`RedisOps.script()` 改为初始化时读取UTF-8文本并设置到脚本对象：

```java
DefaultRedisScript<T> script = new DefaultRedisScript<>();
script.setScriptText(RedisScriptContent.read("lua/" + name));
script.setResultType(type);
script.getSha1(); // 初始化预计算；关键是上面的静态文本，不是单独调用此方法
return script;
```

`compactJournal()` 的 `RedisOps.script("journal_gc.lua", List.class)` 移到字段初始化，只创建一次。所有受理、归还、预热及清理脚本按部署复用；检查是否还有请求热路径 `setLocation` 或临时资源脚本。

不修改Lua内容、KEYS/ARGV、返回值、AOF策略及订单状态。保留完整文本和Spring的EVALSHA/NOSCRIPT回退；不能只保存SHA。资源缺失让服务启动失败。部署内脚本不可变，更改需构建/重启。

**验证**：

- 现有28项交易集成回归全部通过。
- 仅在独立验收Redis测试SCRIPT FLUSH或重启后的NOSCRIPT回退；不清空正在运行的共享Redis。
- 同参数3轮3500突发，所有3500受理并落库，对账通过；逐轮比较P95，先验收≤800ms，再检查是否≤500ms。
- 相同JFR条件下，HTTP调用栈不再触发资源修改时间检查；≥10ms的脚本monitor累计等待较基线下降至少95%作为诊断目标，HTTP门槛仍独立判断。

**回滚**：恢复上一应用包。无数据或协议迁移；保留原待办继续重放。不因成绩暂时未达而恢复动态资源热检查，除非发现功能兼容问题。

## 4. 第2步：将历史扫描改成待归档任务（第二提交）

**修改位置**：`TicketWriter.java`、`TicketPipeline.java`、`lua/journal_gc.lua`（只在必要时调整批次返回）、新增 `db/005-journal-gc-queue.sql`、对应集成用例及回填脚本。

本机 `scripts/start-data-services.ps1` 已遍历执行 `db/*.sql`，新增005必须幂等。Compose的初始化目录仅在首次空数据卷执行；已有卷必须显式执行005并核验表与索引后再发布应用，禁止用删除数据卷代替迁移。

新增任务表建议字段：`order_id`主键、`user_id`、`client_request_id`、`state`、`next_attempt_at`、`attempts`、`last_error`、`completed_at`；索引 `(state,next_attempt_at,order_id)`。字段类型与已有请求表一致。

具体状态流程：

1. 创建/拒绝事务将请求置终态时，**同一数据库事务**写待归档任务，最早执行时刻不早于 `accepted_at+60000`。重试使用同orderId幂等插入，不把DONE改回PENDING。
2. 后台按索引查询到期PENDING任务，每批先取100–200条，执行现有Redis安全GC语义。Redis仍有pending、repair、releaseRepair或fence时，本轮不确认完成。
3. Redis成功返回已清理身份后，在短SQL事务中写原 `tb_ticket_journal_gc` 标记并将任务DONE。两者一起提交。Redis成功、SQL失败时保留PENDING，下轮幂等重放。
4. 未完成项设置退避时间并记录错误类别，避免每100ms反复取同一批失败任务。多实例执行需短租约或任务认领；任何租约都不能替代幂等。远程Redis调用不放在长SQL事务中。
5. 历史回填按请求主键分批检查终态及原GC标记，幂等插入未归档候选。回填有断点和数量报告；在新写路径已启用后进行，校验未入队终态遗漏为0。迟到终态由实时事务补入，不依赖历史时间游标。
6. `gc.mode=queue` 启用新调度；旧扫描保留为受控回退路径，默认关闭。迁移验证通过后不再每秒反连接全历史；低频审计必须有扫描预算。

**验收**：20万历史且无待办时查询P95≤20ms、每次rowsExamined≤1000；100万档位在独立库记录计划与实测。验证迟到完成、Redis清理失败、DB确认失败、两个实例重复取任务、取消重购后旧请求。原永久请求结果和归还去重不能删除。

**回滚**：保留新增表与候选，切回兼容模式；DONE同时有原GC标记，旧逻辑不会丢失已完成信息。停写前排空或保留未完成任务，不DROP任务表。

## 5. 第3步：解除Kafka sender上的清理阻塞（第三提交）

**修改位置**：`TicketPipeline.publish()`、`publish_ack.lua`、`application.yml`、对应故障测试。

先保留现有消息及Stream结构，完成最小改造：

- broker成功回调只将 `{streamId,orderId}` 放入有界确认队列；回调不访问Redis。初始容量10000、批100、周期10ms均可配置，作为实验起点。
- 独立工作线程把已确认成功的身份批量交给Lua执行原HSET/XDEL语义。总执行时长及批大小有界，比较100/250/500的P95与Redis阻塞。
- 队列满或入队失败时保留原Stream并解除进程内sending占位，让原身份可重发；清理失败保留待清理身份，进程退出仍能从原Stream恢复。
- sending集合、确认队列与发送窗口都有上限及最老年龄指标；不得通过无限缓冲换短时成绩。

再根据队头停滞指标处理XRANGE头500：采用带进度的读取和显式待确认重试，或后续独立提交切换Stream consumer group。初版不把“游标向后走”当恢复方案；发送失败、确认丢失与进程退出的原记录必须被重新取到。若用consumer group，组从0创建以覆盖历史，PEL超时认领、确认后XACK/XDEL及积压清理必须完整验收。

**验收**：broker确认→清理P95目标≤50ms，sender调用栈无同步Redis I/O；仍须实测，不能只看代码。测试broker成功但回调/清理前退出、队列满、Redis中断、Kafka停60秒、重复投递。所有已受理身份最终有持久结果，库存不多扣。

**回滚**：清理队列里的事件原Stream仍存在；停新发送、保留未清理记录、恢复旧发布器后按原身份重放。不能批量删除“可能已经发过”的记录。

## 6. 第4步：按证据做后续优化

### 6.1 数据库热点与批量

修改 `RuntimeConfig.java` 将硬编码4消费者改为配置绑定，比较消费批50/100/200；如测500，仍须限制单事务SKU数、参数数量和锁持有时间。记录每批实际大小、事务/commit时间、行锁等待和积压消退速度。

实验Kafka key从orderId改为skuId，让同一SKU在同一分区顺序消费。先停止新受理并排空旧路由，避免切换期间同SKU跨旧新分区并发。热点单SKU可能受单分区限制，分散SKU才会跨分区扩展；以两类场景共同决定是否采用。支付、取消与超时仍会争用库存行，不能因key变更移除数据库锁及约束。

### 6.2 线程、堆与连接

脚本锁修复后再测试HTTP工作线程200/320、Kafka发送批16/64KiB、消费者4/8等单变量。JVM先保持256–768MB做可比A/B；仅在GC/分配证据支持时调整到512MB–1GB或2GB，检查本机剩余内存，不能给16GB主机所有进程同时扩堆。

MySQL池先保留32；本次没有池容量不足证据。真实等待出现后才比较池大小和资源隔离。连接、accept backlog、keepalive需读取运行态验证绑定成功；多开线程不会增加单热库存行的并行修改能力。

### 6.3 结果查询与前端

修改 `TicketAdmission.query/dbResult`、订单展示DTO及 `frontend/app.js`：CREATED时以本人权限返回足够的订单摘要，减少当前“查结果再查订单”的一次往返。未完成结果才退避，优先使用服务端建议间隔，保留随机抖动、60秒上限及隐藏页停止。实际测页面可见时间，不能把轮询优化算作POST受理收益。

### 6.4 何时才动同步查库与分片

只有上述完成后，阶段指标显示请求SQL或连接获取成为主要限制，才考虑新请求免SQL。Redis命中快捷路仅改善重复请求，首次miss仍要查数据库。

真正免SQL需单独设计V2：服务端签名短期请求票据绑定用户、SKU、配置及原请求号；Redis请求墓碑至少覆盖票据有效期，过期/旧协议进入数据库恢复而非重新扣库存。必须覆盖Redis丢失停卖、客户端改参数、跨SKU复用请求号和取消后重放。预计额外2–4天起。

分库分表、Redis Cluster和库存分桶也另开设计。当前一个Hash服务于单条HSET原子证据；直接拆槽会改变全局幂等、全局限流和归还恢复语义。没有测量依据时不作为前四步的默认工作。
