日期：2026-10-20。环境：Windows 11、本机 JDK 17、Redis 6398、MySQL 3318、Kafka 19092，8089 直连。所有成绩为独立验收票种，3500 个已鉴权用户、库存 3600、预建 HTTP 连接；3500 个请求均实际写出，拒绝请求不计入有效受理。

## 已执行改造

- Lua 脚本启动时读取文本并使用预计算 SHA-1；新增不可变 `RedisScript` 实现，避免 Spring Data Redis `DefaultRedisScript.getSha1()` 的同步锁。
- 终态请求在同一数据库事务写入 `tb_ticket_journal_gc_task`，后台按索引领取并在 Redis 清理成功后确认；保留旧扫描作为 `JINGYUE_JOURNAL_GC_MODE=scan` 回退。
- Kafka broker 回调只写有界确认队列，独立任务批量执行原子确认清理；队列满、Redis 失败和进程退出均保留原 Stream 事件。
- 首次唯一请求走 Redis 受理日志快速路径；归档后保留 `done:user:request` 永久幂等墓碑，数据库唯一约束和消费者事务继续作为最终防线。
- Tomcat 工作线程默认从 200 调整为可配置 400；600 线程实验变慢，默认不采用。

## 诊断结论

原始 JFR 显示 200 个 HTTP 线程在 `DefaultRedisScript.getSha1()` 等待，3369 个 monitor 事件；静态脚本代码已消除该资源检查路径。数据库诊断还显示同一 SKU 的消费者在 `tb_ticket_sku ... FOR UPDATE` 上累计等待约 5.6 秒，说明单 SKU 数据库行锁和批量创建仍是后续主要候选。归档队列解决历史扫描的可扩展性，但不会直接消除单 SKU 锁竞争。

下一步应按单变量比较消费批次、消费者数量和按 SKU 分区路由，并重新采集可用 JFR；不能通过继续增加 HTTP 线程或关闭数据库约束换取成绩。
