# 景约票务性能恢复与容量提升 PRD V1.1

日期：2026-10-20。状态：诊断后待实施。基线：票务V1.0功能版；范围仅景约票务与原有点赞回归。本文补充性能需求，不替换V1.0交易、权限和恢复规则。

## 1. 要解决的问题

旧优惠券3500同步突发的HTTP受理P95约518ms；迁移后的票务同类受理约2955ms。用户点击抢购后等待变长，持续流量又会触发背压。已经定位脚本资源检查锁争用与后台历史归档扫描；详见[诊断报告](性能诊断-500ms差异-20261020.md)。

目标是在完整票务规则和消息可靠性不变的前提下，恢复快速受理，降低落库排队，保证历史数据增长和到期归还时仍可持续运行。以测量结果决定是否进入下一层架构改造。

## 2. 用户体验要求

- 点击后100ms内显示“正在提交”并防止重复点击；这是页面反馈目标，不代表受理或落库完成。
- 受理成功但未落库显示“排队处理中”；数据库确认后才显示“下单完成，待支付”。
- 当前详情页自动展示对应票种、日期和订单；刷新保持选择，迟到响应不覆盖新选择。
- 网络超时保留原请求号查询；错误状态有明确重试入口，不能自动创建新意图。
- 支付事务提交后才展示有效票；取消和到期关闭后，仅在可靠归还完成时才允许重新购买。

## 3. 指标与验收口径

| 编号 | 指标 | 验收条件 |
|---|---|---|
| G1 必须 | 恢复V1.0单SKU突发门槛 | 3500个已鉴权用户同步POST，库存至少3500；有效受理及最终创建各3500，系统/网络错误0，写出后未完成峰值≥3000，每轮受理P95≤800ms |
| G2 优化目标 | 向500ms恢复 | 在G1相同条件下，3轮受理P95均≤500ms；历史518ms是约500ms，不能宣称旧版已严格达到500ms |
| G3 必须 | 持续有效受理 | 3000次/秒×60秒，180000个合法用户SKU组合；实际按期注入全部180000，成功率≥99.9%，有效受理P95≤200ms；拒绝不算有效吞吐，停流30秒内完成可靠处理及对账 |
| G4 必须 | 混合购票流程 | 1000鉴权虚拟用户15分钟，至少10000笔有效订单；包含真实退避查询、支付、10%取消、核销；HTTP系统错误<0.1%，订单结果可见P95≤3s，支付与核销P95≤500ms |
| G5 必须 | 历史数据与长时运行 | 在先测得的稳定有效受理峰值50%负载下运行30分钟，保留15分钟到期；无不可排空积压、OOM或库存/资格/订单/支付/票券/核销差异 |
| G6 必须 | 点赞不回归 | 3000次有效状态变更/秒×60秒，最终每用户状态/版本、关系、计数一致；重复空操作不得计数 |

G1/G3/G4/G5/G6均须通过，才能宣称本期全部必需性能验收完成。G2单列为更严格目标，达不到时保留真实数值，不能把目标改成已达成结果。发布功能优化可以先按阶段交付，但状态必须标为部分验收。

“3轮”指相同代码、配置、业务预热、连接预建与数据规模的独立测量，所有结果保留，不只选最快一轮。冷启动另外测，不混入热态统计。稳定峰值定义为在受理时延及正确性门槛内、重复测量无持续积压增长的最高**已测**流量，不使用理论推算或突发3500/0.6秒作为稳定TPS。

## 4. 必须保持的交易约束

1. 鉴权、用户/SKU/全局限流、售卖窗口、配置版本、库存与有效资格校验开启。
2. Redis关键预扣身份和恢复证据仍以原子写入建立；Stream索引失败不能丢掉权威待办。
3. 原请求号跨Redis临时日志归档后仍返回原订单；取消重购后旧消息不能复活。
4. broker成功确认后才允许清理待发送记录。数据库提交或持久隔离后才推进消费位置。
5. 回调、进程或Redis故障允许同eventId/orderId重投；库存和资格最多变化一次。
6. 不通过降低持久化、提前ACK、关闭去重、清空业务数据或把429算成功达标。
7. Redis权威库存丢失继续停卖并对账，不从落后的数据库直接重新灌库存。

## 5. 需求列表与优先级

| 编号 | 优先级 | 需求 | 产出与验收重点 |
|---|---|---|---|
| PF01 | P0 | 部署内Lua不可变加载 | 启动时UTF-8读入文本并复用脚本实例；缺资源启动失败；保留NOSCRIPT回退；消除JAR热检查路径 |
| PF02 | P0 | 可解释的阶段观测 | 区分鉴权、池等待、请求SQL、Lua往返、结果序列化、broker确认、DB提交、页面可见；提供直方图、运行版本与参数 |
| PF03 | P1 | 有索引的待归档队列 | 终态事务产生候选；Redis清理成功后确认；处理迟到终态与积压；历史增长不导致每秒全历史反连接 |
| PF04 | P1 | 有界发送与批量确认清理 | broker回调无同步Redis网络I/O；队列/批次/在途量可配置；失败及队列满保留原Stream |
| PF05 | P1 | 恢复扫描限时执行 | 保留跨轮cursor及权威兜底；按耗时预算调度；恢复最老事件有指标，不以暂停恢复换成绩 |
| PF06 | P2 | 热点SKU数据库写入优化 | 比较50/100/200批次与按SKU路由；测锁等待和事务时间；继续唯一约束、固定锁顺序、整事务重试 |
| PF07 | P2 | 运行参数按证据调整 | 可配置消费者数、HTTP线程、堆、连接及缓冲；每次只改一项，记录实际绑定值和资源余量 |
| PF08 | P2 | 查询及页面结果减时 | 单次结果返回足够的本人订单展示信息，避免CREATED后无必要第二次查询；保留权威与隐私检查 |
| PF09 | 条件进入 | 新请求免同步SQL协议 | 仅在PF01–PF07后仍被查库限制时单独设计V2；明确请求有效期、墓碑持久性、跨GC/跨SKU重试与旧协议兼容 |
| PF10 | 条件进入 | Redis/数据库分片 | 只有单实例或单SKU已被测量证明达到瓶颈才设计；不能只拆Hash或加消费者就宣称扩容 |

PF01直接复用现有 `RedisScriptContent`，不得改Lua业务内容。PF03引入的新状态只管理归档任务，不能替代永久请求去重及归还去重。PF04保留原订单事件格式，减少不必要的发布风险。

## 6. 数据规模与容量要求

- 同时测试空环境基线、20万历史订单、100万历史订单档位；大档位使用独立验收库，不覆盖现有演示数据。
- PF03目标：20万历史且待办为空时不扫描全历史；连续采样查询P95≤20ms、每次rowsExamined≤1000。100万档位也须记录实际计划，若门槛不达则继续优化，不改成无条件通过。
- 待归档任务默认60秒后可处理；健康环境到期后5秒内完成至少99%，批次失败保留重试。未确认投递/归还的身份不清理。
- 归档、修复和ACK清理均有批大小、时间预算、最老待办年龄；后台队列不能无限增长。
- 重复历史资格、终态订单与永久去重保留是合法存储需求；以增长速率和生命周期管理容量，不能将删除安全记录当作性能优化。

## 7. 故障与一致性验收

每次改变可靠链路必须覆盖：Kafka停60秒、broker成功后清理前退出、清理队列满、Redis清理失败、DB提交后ACK前重放、事务中单条SQL失败、GC后原请求、取消重购后旧消息、迟到终态归档、恢复加速索引缺失、支付与关闭竞争。

排空后检查每SKU：总库存=可售库存+有效占用订单；有效资格与占用订单对应；请求身份唯一；支付、票券及核销唯一；Redis与数据库库存一致。对账失败即本轮失败，不用更快的HTTP数据掩盖错误。

## 8. 测试工具要求

负载发生器不能在调度循环内等待慢速监控HTTP请求。当前混合脚本120000笔上限和1000固定用户不足以执行高档位峰值50%的30分钟目标，须先完成有界内存的高容量发生器及足量数据准备；执行方案列出具体修改。业务注入、低频监控、最终审计分别调度，避免监控超时使负载突然补发。记录计划发送、实际发送、未发送、发送偏差、连接池排队、Node事件循环延迟、真实写出在途峰值。

每轮记录入口（8089直连、5190代理）、jar及配置SHA、JDK/Redis/MySQL/Kafka实际版本、CPU/内存、历史数据量、后台积压、线程/池/分区和消费者实际值。诊断开启JFR时单列，不作为正式性能门槛结果。

## 9. 发布、迁移与回滚

按PF01→PF03→PF04/PF05→PF06/PF07→完整验收推进，每阶段有独立构建和基线，不捆绑全部改动后才测。SQL结构变更使用增量脚本；旧历史候选按主键小批回填、断点恢复，并校验未归档终态遗漏为0。

发布前停止新受理，排空或可靠冻结原事件，再切换兼容版本；恢复后检查积压与对账。脚本加载回滚不改数据；归档回滚保留任务与旧GC标记；消息路由变更不能让旧积压和新路由不受控并行。任何V2请求协议回滚必须保留V2恢复入口。

## 10. 当前状态

PF01、PF03、PF04 已实施并完成 28 项交易集成回归；受理快速路径和 Tomcat 线程参数也已完成实验。实测结果见[性能恢复实测报告](性能恢复实测报告-20261020.md)：正式突发 P95 最佳约 1325ms，G1–G6 尚未全部验收，G2 的 500ms 目标未达到。下一阶段按执行方案继续验证单 SKU 数据库锁、Kafka 批次和分区路由，不能把当前阶段结果描述为已恢复 500ms。
