# 景约文旅票务平台产品需求文档

版本 V1.0　编制日期 2026年10月20日　负责人 张乐佳

本文面向产品负责人及后续开发、测试人员，定义将现有黑马点评扩展项目迁移为文旅票务演示平台的开发范围、业务规则和验收方式。首版完成景点发现、游记互动、指定日期门票抢购、模拟支付、订单查询及模拟核销。旅游 Agent 的门票查询和购买跳转在第二阶段接入。

产品暂用名称“景约”，命名可独立调整，不影响业务范围。支付、票券和核销均为演示用途，不接真实收款或景区闸机。本文中的新表、新接口和目标指标均为待开发要求；现有能力单独列明，不代表迁移已完成。

## 1 产品问题与迁移目标

现有项目已经具备高并发受理与异步下单基础，但业务围绕店铺、探店笔记和优惠券。直接换成票务名称，会产生使用日期不明确、票种与库存混淆、下单后不能支付或核销等问题，也无法与旅行规划工具建立可靠关联。

| 问题 | 对用户及项目的影响 | 本次解决方式 |
| --- | --- | --- |
| 优惠券与门票语义不同 | 用户不知道购买的是哪一天、哪种入园资格 | 新增景点、票种、日期库存和订单快照模型 |
| 秒杀受理不等于订单完成 | 超时、排队容易被误认为购票成功或失败 | 区分请求受理、待支付、已出票等状态，提供结果恢复 |
| 缺少交易后续步骤 | 演示只能停留在生成订单号 | 增加模拟支付、未支付取消、超时关闭及核销 |
| 原一人一单集合不能支持取消后重购 | 简单删用户会误释放其他订单的资格 | 用订单绑定资格，新增幂等库存归还机制 |
| 旧修改接口与公开读接口混在一起 | 普通用户可能修改票种、库存或执行核销 | 明确游客、购票用户、运营与核销员权限 |
| 旧压测不能覆盖新增业务 | 不能证明轮询、支付和核销下的处理能力 | 新建票务业务压测、混合负载及故障验收 |

首版成功意味着：用户能够完成一次可信的演示购票流程，开发者能够解释每个状态的来源，并能在异常后查清库存、资格、订单和事件之间的关系。

## 2 已确认范围与产品限制

已确认首版采用完整演示流程，包含模拟支付与模拟核销；Agent 查询和跳转进入第二阶段。以下产品规则作为首版开发默认值，可通过后续版本变更，不作为实现时临时决定。

| 项目 | 首版约定 |
| --- | --- |
| 售卖对象 | 景点、博物馆、文旅场馆的指定日期电子票；无选座 |
| 票种 | 可配置不同展示名称，但首版只提供成人单人票，不做儿童年龄或实名资格校验 |
| 库存单位 | 一个票种在一个使用日期对应一个独立库存 SKU |
| 下单数量 | 每单一张；不支持购物车、多票合单、团体票 |
| 用户限购 | 同一用户对同一 SKU 最多保留一份有效资格；已支付、已核销或过期未使用后不能再买同一 SKU |
| 取消后重购 | 仅未支付订单可以取消；关闭且资格释放完成后，可用新请求重新购买 |
| 支付方式 | 明确标注“模拟支付，不扣真实资金”；不接微信、支付宝或银行卡 |
| 支付时限 | 默认落库后15分钟，且不能超过门票使用窗口结束时间 |
| 退款改签 | 已支付后首版不提供退款、改期和部分退款；购买前明确提示演示规则 |
| 时间与价格 | 业务时区 Asia/Shanghai；日期为当地日期，接口时间含时区，金额统一以整数分保存 |
| 可用端 | 中文移动端网页及简易运营网页；手机宽度360至430像素、桌面1280像素以上可操作 |
| 场景定位 | 独立演示及面试项目；生产商用前需另行完成支付、合规及高可用方案 |

首版不开发真实实名购票、真实出票供应商、座位图、动态定价、优惠券叠加、积分、分销结算、多租户商家体系、跨库事务和跨地域容灾。不使用模型判断是否有库存、是否支付成功或是否可核销。

## 3 用户角色与核心流程

| 角色 | 可执行操作 | 明确禁止 |
| --- | --- | --- |
| 未登录游客 | 浏览景点、票种和公开游记 | 下单、支付、点赞、查询他人订单 |
| 登录用户 | 发布游记、点赞、抢票、查询本人订单、模拟支付、取消未支付订单、查看本人票券 | 修改价格库存、核销票券、访问他人购票结果 |
| 运营管理员 | 管理景点和票种、发布暂停库存批次、查看对账、处理失败事件 | 删除已发生交易的历史订单或无审计地修改库存 |
| 核销员 | 核销被授权景点的有效票券、查看核销结果 | 跨景点核销、修改订单价格、查看无关用户信息 |

用户主流程：选择景点 → 选择票种与使用日期 → 查看购买须知 → 登录并提交抢购 → 等待创建订单 → 模拟支付 → 获取电子票 → 在有效日期由核销员核销。

运营主流程：创建景点与票种 → 配置日期、售价及总库存 → 校验并预热 → 发布销售 → 观察受理和积压 → 必要时暂停 → 对账 → 归档。

异常主流程：结果不确定 → 以原请求查询 → 查到订单则继续；持续未决则进入运营待处理，不自动再下一单，也不按超时直接退库存。

## 5 功能需求

### 5.1 身份与景点发现

**R01 登录与权限　P0**

保留手机号验证码演示登录，明确不发送真实短信。演示验证码仅在开发配置和指定演示账户下可获取，不能开放通用读取接口。验证码校验后失效，增加发送与尝试频率限制。注销删除当前token；请求结束清理ThreadLocal。新增角色检查和景点授权范围。仅公开GET读取，所有管理写操作必须在服务端鉴权。

验收：未登录写操作返回401；普通用户访问管理或核销接口返回403；过期token不能续活；同一验证码不能重复登录；用户不能通过修改URL、请求体userId获取他人订单。

**R02 景点列表与详情　P0**

首页提供景点与游记入口；景点列表支持城市、分类、名称关键词、分页，返回已发布景点。详情包含名称、图片、介绍、地址、坐标、开放时间、入园说明、票种和游记。空结果有中文引导；距离排序复用现有能力，定位不可用时仍可浏览。

验收：停用景点不进入公开售卖列表；直接访问不存在或未发布景点不泄露管理内容；列表和详情不展示旧餐饮占位评价、口味评分或与样例无关的图片。

**R03 票种与日期选择　P0**

详情页默认展示未来30天已配置的日期，支持选定成人票及使用日期。每个日期显示售价、入园时间、销售状态；库存显示“充足、紧张、售罄”或带更新时间的参考数量，提示以提交结果为准。不缓存库存作为抢票资格依据。

验收：不能选未配置日期；日期切换刷新SKU和价格；不同日期库存独立；客户端改价格、日期或票种组合不能改变服务端下单结果。

**R04 游记与点赞　P0**

复用游记发布、列表、详情、作者及图片上传，新增关联景点。点赞/取消为明确目标操作，立即反馈，失败恢复并校正服务端结果；重复点击不重复计数。保留事件版本与取消墓碑。原关注能力可保留入口，但评论、打卡积分不作为新开发重点。

验收：作者只能修改自己的内容；上传限制类型与大小，正文安全展示；批次合并只发生于同一用户和同一篇游记；对账同时核对关系、版本、总数和事件排空。

### 5.2 抢购与订单创建

**R05 可售与限购校验　P0**

每次提交必须验证SKU已发布且完成预热、当前时间处于销售窗口、使用窗口未结束、库存足够、用户没有有效资格、未触发限流或积压保护。边界采用saleStart <= now < saleEnd，统一使用服务器侧可信时间，前端倒计时仅展示。

验收：直接绕过页面调用接口，仍无法购买未开始、暂停、售罄或已结束SKU。暂停停止新受理，暂停前已受理的合法订单继续处理。发布后的价格、票种、日期、有效期及总库存首版冻结，避免处理中事件的商品快照漂移。

**R06 幂等受理与待发送事件　P0**

前端一次购票意图生成clientRequestId，重试、断网恢复和刷新查询复用该值。Lua绑定用户、SKU、订单号及请求参数摘要，并同步维护库存、有效资格和待发送事件。相同用户及请求号、相同参数返回同一处理结果；同请求号不同参数返回冲突。用户ID只取自登录态。

每条事件至少包含schemaVersion、eventId、orderId、userId、skuId、clientRequestId、acceptedAt及售卖配置版本。订单号全程以十进制字符串交给浏览器。已拒绝或关闭的请求号重试返回原结果，重新购买使用新请求号。

验收：同一用户同一SKU的200次并发请求，只有一个有效资格；多个不同请求号也不能突破限购；接收失败不得只扣库存而没有可追踪事件。原脚本恢复日志及屏障随新键结构同步迁移，并通过故障注入验证。

**R07 可靠投递与批量落库　P0**

保留Redis待发送事件至Kafka broker确认。超时属于未知，保留原订单号重试。消费者按SKU固定顺序锁定库存，校验重复与业务身份，汇总扣减，批量插入带快照的订单及有效资格记录，在事务提交后确认消费。

相同订单号且业务匹配时幂等成功；不同身份共用订单号、配置版本不匹配等冲突进入异常处理，不吞异常。Kafka消息按订单ID设置key，后续订单操作以数据库状态机保证顺序，不假设所有同SKU事件处于同一分区。

验收：发送失败、确认丢失、重复投递、提交后崩溃等情况下，合法请求最终创建一个订单；数据库库存不为负。新票务主题、消费组和事件格式与旧优惠券完全隔离。

**R08 受理结果查询与超时恢复　P0**

提交后显示“正在提交”，受理后显示“排队处理中”；数据库订单创建后显示“待支付”，不能直接显示“购票成功”。请求号查询区分PROCESSING、CREATED、REJECTED、UNKNOWN；CREATED携带订单号及订单业务状态。接口未知、网络超时或未查到结果，不自动生成新的购买请求。

首轮轮询在约1秒后开始，依次退避至2、4、5秒，增加0至300毫秒抖动；自动查询约60秒后保留手动查询入口。页面隐藏或离开停止定时器，重新进入恢复。sessionStorage按用户及请求绑定记录，不存支付凭证。支持按本人及SKU查询当前有效申请，处理本地请求号丢失。

验收：收到受理回复但订单尚未落库时，不出现待使用票券；刷新和网络故障恢复不重复POST。待处理超过60秒产生运营关注标记，超过5分钟升级告警；告警不自动释放库存。

**R09 我的订单与订单详情　P0**

提供分页订单列表，可筛选待支付、待使用、已使用、已关闭、已过期；待处理申请单独显示。订单详情展示景点与票种快照、使用日期及时间、成交价格、订单号、创建时间、支付截止时间和可用操作。产品后续编辑不改变已创建订单的快照。

验收：查询范围只属于当前用户；修改订单号不可越权；Long ID不丢精度；订单详情以数据库权威状态为准，关键状态变更后的查询不复用旧的本地状态快照。

### 5.3 模拟支付与资格释放

**R10 模拟支付　P0**

支付页明确展示订单摘要、应付金额和“模拟支付”提示。服务端读取订单金额，前端不提交可信金额或已支付状态。支持演示成功、失败、重复回执；模拟回执产生与校验由服务端控制，开关在非演示环境关闭。

支付事务仅将未到截止时间的PENDING_PAYMENT转为PAID，并写入唯一支付记录、支付时间和一张有效票券。支付失败保留待支付；重复成功回执返回已有支付与票券。支付超时只表示结果未知，前端查询订单，不自行改为支付失败。

验收：伪造金额无效；重复回执不重复出票；关闭订单不能被迟到回执复活；同订单最终支付记录与票券各一份。支付、取消、到期关闭必须竞争同一订单状态，通过事务和条件更新决定唯一结果。

**R11 取消与支付超时关闭　P0**

仅PENDING_PAYMENT可以主动取消。后台按索引分页扫描到期未支付订单，不依赖单机内存定时器或Redis过期通知作为唯一依据；进程重启后补扫。默认每5秒扫描，健康环境到期后30秒内完成关闭，容量不足需告警。

关闭事务包含：订单转为CLOSED及原因、数据库可售库存加一、删除属于该订单的数据库有效资格、写入唯一库存归还事件。Redis由后台原子按orderId核对资格后加库存并释放；重复归还事件不能再次加库存，旧订单事件不能删除新订单资格。DB关闭后Redis尚未同步，页面显示“已关闭，名额释放中”，暂不能重购。

归还脚本也必须覆盖执行中断后的恢复：Lua的原子执行不代表运行时报错会撤销此前写入。库存、资格和去重标记应结合恢复记录及屏障处理，不能在库存已加一、去重标记尚未写入时直接整条重放。资格缺失或指向不同订单且缺少已归还证据时，转入对账，不凭猜测补库存。

验收：支付与取消各自并发100次，最终只可能支付成功或关闭，不能既出票又退库存；关闭操作重试不多加库存；释放完成后允许新请求购买，旧事件重放不得再次扣库存或影响新订单。

### 5.4 电子票与核销

**R12 电子票展示　P0**

支付成功后生成不可猜测的核销凭证，票券页展示景点、票种、指定日期、入园时间、有效状态及二维码。二维码携带随机凭证或签名凭证，不能仅编码连续订单号。普通列表不返回完整核销凭证，日志不记录完整凭证。

票券状态为VALID、USED、EXPIRED。订单取消没有票券；已支付票超过使用结束时间变为EXPIRED，不自动归还已售库存。已支付退款与改期不在首版范围。

**R13 模拟核销　P0**

核销员在独立页面扫码或粘贴演示凭证，服务器验证角色、景点授权、订单已支付、票券未核销及使用窗口。通过条件更新在一个数据库事务中将票券置为USED、订单置为USED并写入核销流水。

验收：同凭证100个并发核销只成功一次；再次核销显示首次核销时间，不再改变业务状态；提前、过期、跨景点、伪造或未支付凭证均拒绝。核销结束边界使用now < validUntil；即使后台未完成过期扫描，接口也必须拒绝过期票。

### 5.5 运营与恢复

**R14 景点票种与库存批次管理　P0**

提供简易运营页面创建景点、票种、日期SKU；校验日期、时间、金额、库存及唯一组合。SKU生命周期为DRAFT、READY、ON_SALE、PAUSED、ENDED、ARCHIVED；售罄为库存派生展示，不替代生命周期。

数据库保存后显式预热库存及售卖元数据，成功才进入READY，达到开始时间才可受理。暂停操作先可靠关闭Redis受理开关，再更新管理状态；任一步失败显示“暂停处理中”并重试。禁止在已有预扣或订单时用MySQL库存覆盖Redis。总库存调整、重新定价及活动中改日期首版不开放，使用新SKU发售。

发布操作必须完成售卖元数据同步并进入ON_SALE，仍由售卖时间限制实际受理；READY本身不允许下单。暂停后恢复原批次只恢复受理开关，不能重新预热覆盖剩余库存。同一票种同一日期只能有一个SKU，不能通过重建同日SKU绕过冻结规则；新方案使用其他日期或明确的新票种，首版不支持同一批次改价重开。

**R15 异常事件处理　P0**

建立可查询的异常记录，包含订单/请求/事件身份、错误分类、重试次数、首次及最近错误、处置状态。暂时故障重试；持续失败进入运营待处理。若实现隔离队列，必须先确认可靠保存原消息、原topic/partition/offset及原因，才能越过原消费位置。

受理后无法创建订单时，不可直接显示失败并退资格。运营拒绝必须在数据库写入持久拒绝记录，并在同一事务写出对应释放事件；消费者创建订单前检查拒绝记录。拒绝与创建使用同一订单身份的数据库互斥/唯一状态协议，保证迟到消息不能创建已拒绝订单。未曾扣减数据库库存的申请，只归还Redis预扣，不能给MySQL额外加一。

**R16 对账与运行概览　P0**

运营页面展示每SKU总库存、数据库可售库存、Redis可受理库存、处理中申请、待支付、已支付、已使用、关闭、异常与待归还数量。观察Redis待发送、Kafka各分区lag、最老未处理事件年龄、归还事件积压及预扣恢复屏障。

提供只读对账与可审计的重试入口；不提供一键清库存、清用户资格。所有发布、暂停、拒绝、重试、核销写入操作者、业务对象、前后状态及时间。默认告警先写入受限运营页面和日志，不自动向外部人员发送消息。

### 5.6 缓存与运行保护

**R17 缓存一致性　P0**

景点详情、票种文案使用L1 Caffeine、L2 Redis，数据库为权威；本地TTL建议30秒、Redis TTL建议120秒并增加抖动，均可配置。数据库提交后执行可靠失效，多实例通知清理本地缓存，通知缺失由TTL及监控兜底。失效事件从数据库事务中写入的待办产生，不能只依赖afterCommit回调内一次发送。

使用内容版本与回填校验防止较旧响应覆盖已知新版本。共享重建代码先修复锁归属，获得锁后再次检查缓存。登录授权、库存受理、支付、核销判断不依赖公共本地缓存。缓存的更新时间不等于业务事实发生时间。

验收：更新后健康环境各实例5秒内展示新内容；暂时丢失广播但共享Redis失效成功时，本地TTL到期后读取新值。并发旧读、删除失败和重建故障单独注入验证；不承诺异步缓存严格实时一致。

**R18 限流与背压　P0**

复用ZSet滑动窗口与唯一member修复，按用户、SKU及全局配置受理速率，并针对订单查询、模拟支付、核销设置独立配额。阈值在压测前配置，测试数据不通过关闭鉴权伪造吞吐。

背压同时观察Redis待发送和Kafka提交进度，采样过旧或异常时降低/暂停受理。Kafka消费者落后时，不能因Redis outbox为空就继续无限接收。达到上限在预扣前拒绝，HTTP429返回中文说明及建议重试间隔。Redis不可用时停止票务受理，不直接把洪峰转发MySQL。

**R19 复现与交付　P0**

提供独立启动配置、环境检查、初始化脚本、演示数据、账号说明、迁移及回滚手册、接口说明和测试报告。新接口使用明确的业务错误码及中文message，前端依据错误码识别确定拒绝、处理中和未知，不再匹配中文错误文本控制流程。

验收：新环境可从文档完成初始化；一键演示数据脚本可重复执行且仅操作新库；清理脚本限定测试命名空间，不删除原项目数据。

### 5.7 第二阶段的 Agent 联动

**R20 景点标识关联　P1**

建立Agent使用的地图POI与平台attractionId映射，包含来源、匹配状态和人工确认记录。不能只依赖景点名称模糊匹配，将同名异地景点关联到错误门票。Agent仓库与接口尚待第二阶段勘查，不假设当前存在可直接调用的工具。

**R21 门票查询与购票跳转　P1**

新增只读工具按景点及日期查询可售票种、参考价格、销售状态、数据时间和白名单购买链接。未售票、无匹配、超时分别返回明确状态。Agent生成行程时可附购票链接，由用户在票务网站登录并确认购买；模型不执行付款、核销，也不承诺余票。

**R22 联动验收　P1**

验证正确景点与日期、不可售不推荐、同名景点不误匹配、接口失败不虚构价格，以及从行程跳转后的重新报价与库存校验。票务服务不可用不阻断基础行程生成，应显示“暂无法查询门票”。

## 6 关键业务状态与并发规则

### 6.1 商品时间规则

一个SKU对应一个票种和一个使用日期，可有固定入园时间范围，例如2026年11月1日09时至18时；首版不支持同一天多个独立场次。saleStart必须早于saleEnd，saleEnd最迟为validUntil前15分钟。使用窗口必须属于指定当地日期，跨日夜场暂不支持。

售卖结束前受理的合法事件允许稍后创建订单。payDeadline取订单创建时间加15分钟与validUntil中的较早值；若创建时已过validUntil或剩余支付时间少于60秒，进入持久拒绝和资格释放流程。已发布数据不可变，消费端按照受理时的配置版本判断，不能用后来的暂停状态否定此前合法受理。

### 6.2 请求状态与订单状态分离

| 层级 | 状态 | 用户含义及后续 |
| --- | --- | --- |
| 请求 | PROCESSING | 已有受理证据，等待落库；继续查询 |
| 请求 | CREATED | 查到数据库订单；跳转订单详情，继续看订单业务状态 |
| 请求 | REJECTED | 有确定拒绝记录与原因；释放完成后才允许新意图重购 |
| 请求 | UNKNOWN | 无法确认；保留原请求继续查，不声称已失败 |
| 订单 | PENDING_PAYMENT | 数据库已提交，库存已扣，等待模拟支付 |
| 订单 | PAID | 已模拟支付并出票，等待核销 |
| 订单 | USED | 已核销，终态 |
| 订单 | CLOSED | 未支付取消或到期关闭，终态；另列释放状态 |
| 订单 | EXPIRED | 已支付但超过使用有效期，终态，不归还当日已售库存 |

允许转换：PENDING_PAYMENT到PAID或CLOSED；PAID到USED或EXPIRED。其他转换拒绝。超时关闭与支付并发时，只能有一方成功更新原状态。已关闭订单保留原请求结果和历史，不能删除后伪装为从未下单。

### 6.3 限购与归还的核心不变量

同一用户同一SKU最多存在一个有效资格。资格绑定orderId，取消只能释放对应订单。已支付、已核销、已过期的票仍占用该SKU的限购资格；取消或未支付超时完成释放后可重购。数据库订单历史因此允许同一用户与SKU存在多条已关闭订单，不能直接沿用旧UNIQUE(user_id,voucher_id)到全部票务订单。

新增有效资格表，主键为(user_id,sku_id)，value保存orderId。创建订单时在同一事务插入资格；关闭时按orderId条件删除。Redis对应用户到订单号的映射，只在归还原子脚本核对匹配后删除。Redis释放晚于数据库提交，期间允许暂时少售，不允许先释放再提交导致超发。

库存归还事件有唯一eventId及orderId，Redis保留“已归还”标记并原子去重。标记在SKU完成停售、使用结束、事件排空且超出允许重放窗口后才允许归档清理；不得随手设置短TTL让旧事件重新加库存。Redis完整丢失时暂停SKU，执行对账恢复；不能把仍可能重放的旧归还事件应用到新预热库存。

支付和核销不再扣库存。已创建订单重复消费，包含CLOSED订单，也不得再次扣库存；消费者必须检查原订单的业务身份和终态。

创建、关闭与补偿路径必须在技术设计中统一跨订单、SKU及资格记录的加锁顺序，批次内部使用稳定排序。数据库检测到死锁时，回滚并有限重试整个事务，不能只重试最后一条SQL或提前确认消息。事务内不等待Kafka确认或执行远程网络调用。

### 6.4 异常拒绝与迟到事件

若合法受理最终无法创建订单，系统必须保留一条以orderId唯一的请求结果记录。拒绝事务与创建事务共享该记录或等效的数据库唯一状态门槛，拒绝成功后，任何迟到的创建事件只能读取拒绝结果并确认，不能再创建订单。

“5分钟没有订单”本身不构成确定失败证据。无法确认的冲突由运营处理并保留证据；如果无法证明归还安全，冻结该SKU并显示待确认。自动补偿的判定必须能区分“仅Redis预扣”和“数据库已经扣减”两种情况。

## 9 迁移实施与数据保护

### 9.1 迁移路线

在实际新代码基线冻结后建立独立迁移分支或工作副本，先迁模型与接口，再迁页面，最后接入完整交易生命周期。本文仅编写需求文档，不授权直接执行数据库迁移。

新演示环境使用独立MySQL数据库、独立Redis实例和独立Kafka主题/消费组。Redis逻辑库不足以替代全部隔离，特别是Pub/Sub及旧硬编码键；迁移时统一配置命名空间。核心售卖仍按单机Redis部署，Cluster多键同槽设计不在首版完成范围。

采用增量建表，保留用户、笔记与点赞基础代码，新增票务实体和服务。不做一次性全仓库Shop/Voucher字符串替换。对外接口走文旅DTO，内部兼容映射通过服务层管理。不得让旧券消费者读取新票务事件，或让同步与异步点赞写入模式同时操作同一份数据。

### 9.2 数据准备

准备至少12个演示景点、3个分类、3个城市、每景点1个成人票产品、未来7至30天日期SKU、12篇游记，以及普通用户、管理员、两个不同景点核销员。库存与金额明显标为演示数据；图片来源与授权记录到素材清单。不得把旧餐饮商户批量改名后伪装成真实景点资料。

原数据默认不导入新业务库。若后续保留旧内容，使用显式ID映射与人工分类，保留历史匿名点赞基数，不伪造点赞用户。迁移程序先执行只读检查，输出插入、跳过、冲突数量；重复运行不重复建记录。

### 9.3 发布与回滚

发布顺序：备份与版本标记 → 新库建表和种子数据 → 关闭售卖下启动后台 → 检查消费者与恢复任务 → 预热指定SKU → 功能与故障验收 → 性能验收 → 开放演示入口。

回滚顺序：停止新受理 → 排空或可靠冻结已受理消息与归还任务 → 核对订单库存 → 切回兼容版本。新版本一旦产生真实演示交易，不能直接丢弃数据库或倒回旧快照；旧券版不理解新票务事件时，只能恢复独立旧入口，不能接管未完成票务业务。

上线门槛包含脚本可重复执行、受理暂停有效、鉴权检查通过、未完成事件有去向、原项目数据未改变以及恢复手册可执行。

测试用受理配额必须覆盖目标流量，仍保持限流逻辑开启；另设超额测试验证429及积压保护。测试前列出用户与SKU数量，确保180000次持续受理均有合法资格；长时间测试另行准备足量组合。分别报告成功受理、库存不足、限流、业务冲突和系统错误，不能将正常拒绝计入有效下单吞吐。
