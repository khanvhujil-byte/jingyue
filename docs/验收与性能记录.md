# 验收与性能记录

## 环境与口径

2026-10-20，本机原生Windows；i7-14650HX、16GB内存；JDK17、MySQL8（独立3318，buffer pool 256MB）、Redis8.8.0（独立6398，512MB/noeviction；2026-10-20只读核实）、Kafka2.5.1单broker/16分区、8089后端及5190前端。负载发生器与服务共享主机，不代表生产集群容量。

真实HTTP压测使用测试fixture准备账号和token，仍走原鉴权、限流及库存逻辑，没有关闭保护。`peakWrittenAwaitingResponse`表示请求已经写出且尚未收到响应的客户端峰值，不能称为处理线程数；服务处理线程峰值由独立metrics记录。

## 最终回归与长时结果

最终 `TicketIntegrationTest`：**28 tests，0 failures，0 errors，0 skipped**，含受理恢复、缓存失效/重建故障、时间窗口及客户端伪造参数校验。原始简表：output/verification/integration-final.txt。

30分钟原始报告：mixed-1792443420280.json。1000鉴权用户按50意图/秒调度，89999笔有效订单全部创建；76499次支付、9000次主动取消、4500次留待超时，2550次核销。271191次HTTP请求均为200，无链路异常。90个SKU审计全部满足库存恒等式和资格对应，支付/票券/核销差异为0，超过截止时间30秒仍待支付为0。

前15分钟已观察到44946笔创建，超过10000目标。创建结果可见P95约1152ms、支付P95约149ms、核销P95约225ms；全30分钟分别约1152ms、147ms、332ms。创建指标包含真实退避轮询，不能当作数据库纯写入耗时。全程最慢创建观察约12.54秒，出现在运行中消费者调整等长尾；P95达标不代表每一笔都在3秒内。

资源采样详见mixed-resource-summary.json：记录堆内存范围、Redis首尾、连接等待与处理峰值。合法订单资格和永久去重会占用存储，内存有增长并不自动等于泄漏；本轮无OOM或无法排空积压。

长时运行期间验证过临时8090实例，长时后的对账、缓存配置及扫描修复另经28组最终回归；不把该轮压力记录描述为最终二进制不间断30分钟的重新测量。
